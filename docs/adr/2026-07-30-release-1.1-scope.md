# ADR: Release scope decisions (grilling session, 2026-07-30)

Sharpened via `/grill-with-docs`. Grounded against code as of `release-1.1.0` branch.

## 1–2. macOS app blocking: fullscreen + backgrounded-tray bug

**Status: root cause confirmed via diagnostic logging (2026-08-03). Fix not
yet implemented — scoped here for release 1.1.0, implementation is a
separate follow-up.**

Originally reported as two separate bugs (fullscreen target app not blocked;
blocking of other apps stops while Flow Fusion is in tray), but the diagnostic
run showed **one shared root cause**, not two:

`AppBlocker.blockApps` in [`MainFlutterWindow.swift`](../../macos/Runner/MainFlutterWindow.swift)
calls `NSRunningApplication.hide()` / `.terminate()` on the target process.
Temporary diagnostic logging (tick timestamps in
[`app_blocker_service.dart`](../../lib/controllers/app_blocker_service.dart) +
per-attempt state in the Swift `blockApps`) showed, across a ~4-minute live
session blocking Telegram:

- The Dart `Timer.periodic` **fires reliably every 2s throughout**, including
  while `NSApp.activationPolicy() == .accessory` (tray mode) — the polling
  itself is not the problem, ruling out App Nap / isolate-suspension theories.
- `hide()` and `terminate()` **returned `false` on every single attempt**,
  and the target process's `isTerminated` **never once flipped to `true`** in
  the entire run. The app was never actually closed — not once, in any state.
- A follow-up check of the macOS unified TCC log for the same time window
  showed **no `kTCCServiceAppleEvents`/Automation request from Flow Fusion
  targeting Telegram at all** — the OS isn't even being asked for permission.

**Conclusion:** `NSRunningApplication.hide()/.terminate()` targeting an
unrelated third-party process is a no-op under App Sandbox
(`com.apple.security.app-sandbox = true`) — this is not a permission the user
can grant via a system prompt, because the call doesn't go through the
Automation/Apple-Events consent flow at all; sandboxed apps simply don't have
this capability via the raw Cocoa API. What looked like "blocking working"
before was **`NSRunningApplication.current.activate()` stealing focus and
visually covering the target window with our own** — a side effect, not a
real hide/quit. Fullscreen (own Space) and tray mode (no window to raise)
each independently defeat that focus-stealing illusion, which is why both
were reported as failures — they're two symptoms of the same non-functional
core mechanism, not two separate defects.

**This matches prior art already in the codebase**: site-blocking
([[macos-site-blocking]]) hit the identical sandbox wall for a different
target (browser tabs) and solved it by switching to **AppleScript/Apple
Events** (`tell application ... to ...`), which *does* work under sandbox via
the `com.apple.security.automation.apple-events` entitlement (already present)
plus a per-target-app Automation permission prompt the OS shows on first use.

**Planned fix direction (not implemented yet):** rewrite `AppBlocker.blockApps`
to send `tell application id "<bundleId>" to quit` via `NSAppleScript`/Apple
Events instead of the direct Cocoa API, mirroring the site-blocker's approach.
Expected side benefit: an Apple Event `quit` isn't tied to window-server focus
the way `hide()` is, so it should also address the fullscreen (own-Space)
case without needing the `activate()` workaround at all. Still needs design
attention on: the per-target-app Automation permission prompt UX (first time
blocking each app), and behavior when an app refuses to quit (e.g. shows an
unsaved-changes dialog) since AppleScript `quit` is also a polite request, not
a force-kill.

**How to apply:** don't schedule the fullscreen/tray items as separate tasks —
they're one fix. Do not implement the Apple Events rewrite silently as a
drive-by; it's native-layer work explicitly deferred out of this grilling
session per the user's request (2026-08-03) to record it in the spec only.

## 3. Instant end-session button

Must route through the same `stopBlocking()` path as the normal
end-of-session flow ([`ActiveTimerController`](../../lib/controllers/active_timer_controller.dart:484)),
not a separate shortcut — otherwise blocked apps can stay locked after the UI
shows the session as ended.

## 4. Menubar timer

macOS via `tray_manager.setTitle()` (package already a dependency, just
unused for title). Windows has no equivalent menubar text — tooltip update
only, or macOS-only scope. Needs `TrayService` to subscribe to the active
timer's tick stream rather than staying a passive singleton.

## 5. Tasks

Scoped down significantly after clarification:
- Exactly **one task per session** (no sub-interval switching within a timer).
- Task is a plain tag for time aggregation — **no status** (no done/archived).
- New `Task` table (id, name) + FK on `Session`, drift migration, a picker at
  timer start (mirroring `blocked_apps_picker.dart`), and a report view
  summing session durations per task.

**Why small:** originally looked like a parallel todo subsystem; the actual
ask is time-tracking-by-tag, which reuses the existing `Session` entity
instead of inventing new state machinery.

## 6. Usage analytics

**Decision (revised):** self-hosted analytics backend (e.g. PostHog or
Umami), events sent via a plain `http.post` to the self-hosted `/capture`
endpoint — **no analytics SDK**. Two constraints ruled out the mobile-first
SDKs from the earlier round:
- App is **desktop-only** (macOS + Windows) — Firebase Analytics has no
  desktop Flutter support at all; Yandex AppMetrica's official Flutter plugin
  is mobile-only (iOS/Android), unconfirmed for macOS/Windows.
- Must be reachable from **Russia** without relying on a foreign SaaS domain
  that could be geo-blocked. Self-hosting (on infra the user already
  controls) sidesteps both the desktop-SDK-support gap and the RU-reachability
  risk in one move — a raw HTTP POST works identically on every platform
  `http` package supports, so there's no SDK compatibility question left.

Still opt-in at onboarding (unchecked by default) per the earlier privacy
rationale — self-hosting doesn't change that the audience is
distraction-blocking/privacy-sensitive. Events must stay anonymous (no
device-stable ID beyond what's needed for dedup, no PII).

**How to apply:** don't add `posthog_flutter` or similar SDKs as a
dependency — just `http` + a small event-shape wrapper.

## 7. Timer progress circle

Root cause of "doesn't reflect real time left": `progress` in
[`TimerProgressCircle`](../../lib/ui/views/timer_view/widgets/timer_progress_circle.dart)
updates on the same ~1s tick as the countdown, no sub-second interpolation —
so the arc steps instead of sweeping. Fix is an `AnimationController`/`Tween`
between ticks, *conditional on* confirming the underlying `progress` value is
arithmetically correct first (don't animate a wrong number smoothly).

## 8. Metro-flow queue fill animation

Refers to [`TimerQueueItem`](../../lib/ui/views/timer_view/widgets/timer_queue_item.dart) —
the station-line queue on the timer screen. Current state transitions
(`isDone`/`isCurrent`) already crossfade color via `AnimatedContainer`, but
that's an instant-value crossfade, not a directional fill.

**Decision:** the connector line between the current and next station must
fill in real time, driven by the current timer's elapsed-progress fraction
(train-on-the-line metaphor), not a fixed-duration cosmetic wipe. This shares
its progress source with item 7 — worth wiring both off one smooth progress
value rather than solving twice.

## 9. Social links in sidebar

No open questions. Implement as a configurable list (icon + URL), not a
hardcoded single GitHub widget, since Discord is a known near-term addition.

## 10. OTA update localization not picked up

**Root cause confirmed** (no diagnosis needed, found directly in code):
[`LocalizedReleaseNotesLoader._resolveLanguage()`](../../lib/model/datasources/update/release_notes_loader.dart)
fell back straight to `'en'` when the user had never explicitly set a
language in Settings, instead of resolving the system locale — same pattern
already handled correctly in [`TrayService._loadL10n()`](../../lib/ui/app/tray_service.dart).
GitHub Pages deploy (`release.yml`) publishes both `release-notes.en.json`
and `release-notes.ru.json` correctly, so it wasn't a publishing gap.

**Confirmed by the user:** the rest of the app's UI locale already resolves
correctly for RU users who never touched language settings (via some other
path not traced here) — so the fix was scoped to just the release-notes
loader, not `AppViewModel.init()`. **Fixed**: `_resolveLanguage()` now falls
back to `WidgetsBinding.instance.platformDispatcher.locale.languageCode`
before defaulting to `'en'`.
